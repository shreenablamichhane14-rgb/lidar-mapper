# Architecture proposal judgements

Three independent judges read all three proposals (ship-first, fidelity-first, ux-first), SPEC.txt and the research data (docs/research/raw and verify), and scored each proposal 1 to 10 on six criteria.

## Judge: CI engineer (compile on CI without a Mac)

Winner: **ship-first**

| Proposal | Spec | Build | Perf | UX | Risk | Parallel | Total |
|---|---|---|---|---|---|---|---|
| ship-first | 7 | 9 | 8 | 7 | 8 | 9 | 48 |
| fidelity-first | 9 | 4 | 5 | 7 | 7 | 5 | 37 |
| ux-first | 8 | 6 | 6 | 9 | 7 | 8 | 44 |

**ship-first**: Easiest of the three to compile. There is no Metal, no SceneKit and no macros. Per-face colors use LowLevelMesh parts plus UnlitMaterial, which rendering-viewer verify confirms needs no shader: 'per-face colors via one material per color ... LowLevelMesh.Part materialIndex (iOS 18.0) need no shaders'. Build 3 uses QuickLook instead of a custom renderer. The shared types are written out as real Swift declarations, so parallel agents can code against exact spellings. There are 38 small modules (under 600 lines each), each agent edits only its own folder plus a Copy+X.swift extension, and M30 is the only owner of project.yml. Estimate: 1 to 3 CI round trips per module and about 3 to 5 integration runs for build 3's 19 modules. Build 3 uses RoomCaptureView(frame:arSession:), which is the path the verify files say is most likely to keep the session config: 'it may hold for the view path, it does not hold for the headless session' (verify/arkit-mesh-depth.json). It also re-applies the config in didStartWith, runs a watchdog, and falls back to a two-pass scan. Plane detection is off for rooms, which is correct. Run-time cost is lowest because Apple's renderer draws the live view and texturing is CPU cell and atlas baking. Weaknesses: (1) The keyframe JPEG is encoded synchronously on the ARKit delegate queue. verify/texturing.json says to 'keep JPEG encode off the ARSession delegate thread on a serial utility queue with a bounded keyframe budget'. (2) There is no large-object path for vehicles and appliances, so large objects get no crop or dimensions. (3) Plan edits (plan.edited.json, a whole-plan snapshot) and 3D overrides (overrides.json) are separate stores that can diverge. (4) Backup uses the in-memory ZipWriter. (5) Texture work only lands in B5 and B6. (6) It writes $INSUNITS into a DXF R12 file, but verify/floorplan-cad.json says '$INSUNITS is not an R12 header variable'.

**fidelity-first**: Covers the most of the spec, and every heavy stage has a fallback. Honesty features: a mesh-refined clean model with acceptance tests, a SurfaceEvidence map built by ray casting (which makes HIDE FURNITURE honest), and hole-fill provenance. Also: counters, cabinets and columns, gravity-constrained ICP for aligning rooms, k_cal calibration, a pose-drift term, and anchor-local lossless raw mesh. It is the only proposal that plans per-room alignment transforms after StructureBuilder. Buildability is the weakest of the three. Render.metal (a vertex-color CustomMaterial) is in build 3, and Texture.metal (a depth render pass with off-axis projection plus compute kernels) is in build 4, with no local compiler. The CI 'Compiler errors' step only greps '.swift:line:col', so Metal errors land in the unsorted 'other' bucket. The vertex-color path is still 'needs device test ... confidence: unsure' (verify/rendering-viewer.json). Core is a single 1200-line bottleneck, and its types are given as tables rather than Swift. Some referenced types are never defined (Segment3, ConfidenceLevel, 'stage timings'). PipelineStage uses associatedtypes, so a heterogeneous scheduler would need type erasure. Capture, Processing and Texture are each split across two agents in one folder, which invites merge conflicts. Estimate: 6 to 12 CI round trips for Texture and Render alone. Run-time cost is the highest of the three: MPS sharpness on every keyframe, a 10 Hz pose track, hi-res stills, a 5 Hz depth stream at Maximum, ICP, and optional TSDF. The exposure cap (1/120 s via configurableCaptureDeviceForPrimaryCamera) is never checked against RoomPlan re-running the session or against tracking in dim rooms. 'Remove original photos' breaks the raw-never-modified constraint.

**ux-first**: Best amateur UX. The quality sheet sits over the live camera, so SHOW MISSING AREAS has a still-running session. Results arrive progressively (clean model and plan first). Degraded modes are designed into the UI, and there is a small/large object chooser. SectorCoverage on the large-object path delivers the spec's 'Capture the left side / back', which Object Capture cannot, as the proposal itself admits. There is one undoable EditLog shared by the 3D view and the plan. For parallel work, the ScanEngine/LiveScanSnapshot contract plus FakeScanEngine and SnapshotRecorder lets UI agents compile and demo on the phone without capture code, and Core is written as Swift. Buildability risks: (1) `@MainActor protocol ScanEngine` makes conforming engines main-actor-isolated by inference, yet RoomScanEngine 'builds a LiveScanSnapshot on capture.queue'. verify/storage-deploy.json says actor-isolation violations 'are hard errors even in Swift 5 mode'. (2) A file named Render/Viewer/Picker.swift invites a type that shadows SwiftUI.Picker across the whole single-module target. `ScanSettings.Range` shadows Swift.Range inside that type. (3) New keys are added directly to the shared Copy.swift, which will conflict when agents merge. Performance: a live ARView with a LowLevelMesh coverage overlay, custom RoomPlan outline boxes, RoomPlan, mesh, and synchronous JPEG encoding on capture.queue is the heaviest live load of the three. Capture risk: `planeDetection = [.horizontal, .vertical]` for rooms, while research says 'if plane detection is also enabled ARKit flattens the mesh where it detects a plane' (raw/arkit-mesh-depth.json). It also uses the headless RoomCaptureSession with isCoachingEnabled = false from build 3, which is exactly the path where sceneDepth is reported dropped. Textures arrive late (B5), and House mode later still (B6).

### Ideas to graft

- From ux-first: Adopt the ScanEngine/LiveScanSnapshot value contract with FakeScanEngine and SnapshotRecorder (demo mode that replays recorded device snapshots). Make the protocol non-isolated. Keep only a @MainActor facade ObservableObject, which receives Sendable snapshots through DispatchQueue.main.async or `Task { @MainActor in }`. Why: UI, Guidance and QualityUI agents can then compile and exercise every scan screen with no ARKit code, which removes the biggest serial dependency in ship-first's build 3 (M30, M34 and M35 waiting on M10 and M15). A non-isolated protocol avoids the Swift 5 hard error on actor isolation that UX-first's @MainActor protocol would trigger.
- From ux-first: Replace in-memory ZipWriter backups with a file-handle StreamingZip (STORE), and use NSFileCoordinator .forUploading as a zero-code fallback for sharing a folder. Why: The existing ZipWriter's `finish() throws -> Data` builds the whole archive in RAM. A house package is several GB (200 to 500 MB per room), while verify/storage-deploy.json says to 'Plan the Object Capture and mesh pipeline for a budget of about 2.5 GB'.
- From ux-first: Use one EditLog (ordered EditOperation list with an undo cursor) applied by pure functions to both CleanModel and PlanModel, instead of ship-first's separate overrides.json and plan.edited.json snapshot. Why: A wall moved in the plan then also moves in 3D Clean. Re-deriving after a rescan replays the operations instead of asking 'keep edited plan?', and edits stay overlays, so raw data is never touched.
- From ux-first: Add a small/large object chooser. Large objects use the mesh driver with a user-tapped seed, a gravity-aligned OrientedBox.fit(_:gravityAligned:), SectorCoverage (8 azimuth sectors plus top), and a crop stored as an edit. Why: The spec requires vehicles, appliances and equipment, plus 'Capture the left side / Capture the back' guidance. Object Capture is capped at .reduced (verify: 'On iOS, only one detail level, .reduced, is currently supported') and exposes no camera pose for side guidance.
- From ux-first: Write in-progress captures to Library/Application Support/InProgress and move them into the package on Finish, then write SEAL.json (file list and sizes) and verify it on open. Do not use POSIX read-only permissions. Why: Files never shows half-written chunks, and raw immutability can be checked. Skipping chmod avoids the Delete/Duplicate failure described under UX-first's flaws.
- From ux-first: After assigning `arView.session = hub.session` for LiveMeshScreen, re-assert the hub as delegate and log `session.delegate === hub`. Why: ARSession.delegate is 'a single weak slot, so whoever assigns last wins' (verify/roomplan.json). Ship-first switches between RoomCaptureView and ARView on one running session for patch passes.
- From fidelity-first: On accepted keyframes, memcpy Y/CbCr, depth and confidence into a small CVPixelBufferPool (4 buffers) inside the callback, then JPEG-encode on the io queue. Drop the keyframe if the pool is exhausted. Why: verify/texturing.json: 'keep JPEG encode off the ARSession delegate thread on a serial utility queue with a bounded keyframe budget (drop, never queue unbounded)'. Ship-first encodes 10 to 30 ms synchronously on the delegate queue.
- From fidelity-first: Store raw mesh chunks anchor-local plus the anchor transform, and make world space a derived product. Record per-frame intrinsics, exposure, a sharpness score and a 10 Hz pose track in raw. Why: It stores exactly what ARKit delivered, which honours 'never destroy the original raw scan'. It allows later re-posing (alignment or ICP) without precision loss, and gives the confidence model a real drift term (path length between observations).
- From fidelity-first: After StructureBuilder, compute and store a per-room rigid transform (from structure.json back to each capture's session frame) by matching surface identifiers that the merge keeps. Apply it to mesh, keyframes and textures. Why: verify/floorplan-cad.json: after merging, 'the first room will be transformed and thus moved around' and 'Room and floor identifiers are regenerated, while wall, door, window, opening and object identifiers are kept'. Ship-first builds CleanModel from structure.json but leaves the mesh and textures in session frame, so House-mode Realistic and Clean would not line up, and overrides keyed by room IDs would be orphaned.
- From fidelity-first: Add a list of forbidden names (Measurement, Transform, Entity, Scene, Material, Object, Surface, Section, BoundingBox, CapturedRoom, plus SwiftUI names such as Picker and Section) and a DerivedIndex with {pipelineVersion, inputHash} per product. Why: All code is one module and one target, so one shadowing type breaks every file. Input hashes let a new pipeline version rebuild only what changed.
- From fidelity-first: As a B6+ stage, add mesh-refined wall and ceiling values with strict acceptance tests (keep both RoomPlan and refined values), and a SurfaceEvidence grid computed by BVH ray casting to drive the measured, occluded and unscanned labels. Why: Ship-first's ceiling is always inferred, and its occlusion honesty is a proximity heuristic. The spec wants ceiling height and 'INFERRED / OCCLUDED / UNSCANNED' distinguished honestly.
- From fidelity-first: Build 3 Diagnostics should include projection dots on the live image, a depth reprojection round trip under 0.5 px, and a numbered UV checkerboard. Why: verify/texturing.json says RealityKit UVs are 'Likely bottom-left ... needs device test'. Settling this before the texture build saves several texture-debug CI and device cycles.
- From research (none of the three): Offer an optional per-room reference length: the user enters one tape-measured distance, and the app stores a reversible scale factor in edits/. Why: verify/roomplan.json recommends: 'include an optional user-driven correction: let the user enter one known reference length ... apply a uniform scale factor ... record the correction in the project file so it is reversible'.

### Fatal flaws

- ship-first: House-mode merge re-bases rooms, but the raw mesh, keyframes and textures stay in the ARSession frame, and overrides keyed by room IDs lose their target. Evidence: verify/floorplan-cad.json open question (a): 'the first room will be transformed and thus moved around to fit in the world space' and 'Room and floor identifiers are regenerated, while wall, door, window, opening and object identifiers are kept ... keep your own copy of the input rooms, and match merged output back to them through the kept surface identifiers'. Ship-first 3.3: 'Success stores derived/structure.json and the CleanModel is built from it', with no transform back to the mesh frame. Overrides.roomNames is keyed by 'RoomPlan identifiers or our ids'. Fix: In M28, match wall, door and window identifiers between each input CapturedRoom and the merged structure. Solve a yaw plus translation per room, store it in derived/structure_alignment.json, and apply it in M22, M26 and M31. Key overrides on our own RoomRecord.id and on the kept surface identifiers, never on RoomPlan room or floor IDs.
- ship-first: Backup and restore of multi-GB packages goes through the in-memory ZipWriter. Evidence: ios/Sources/Export/ZipWriter.swift: `func finish() throws -> Data` and `static func archive(_ entries: [(name: String, data: Data)] ...) -> Data`. verify/storage-deploy.json: 'Plan the Object Capture and mesh pipeline for a budget of about 2.5 GB'. Ship-first's risk 9 puts storage at 200 to 350 MB per room. Fix: Add a file-handle StreamingZip writer and reader in M38 (streaming CRC32 per entry, data written with FileHandle) and keep ZipWriter only for small exports.
- fidelity-first: Metal source files in builds 3 and 4, with CI as the only compiler and a CI script that neither installs nor reports on the Metal toolchain. Evidence: Build 3 ships Render.metal (the CustomMaterial vertex-colour preview). Build 4 ships Texture.metal (a depth render pass plus compute kernels). verify/rendering-viewer.json on params.geometry().color() with LowLevelMesh: 'needs device test ... no compiled iOS sample found', confidence 'unsure'. .github/workflows/ios-build.yml only extracts errors matching '\.swift:[0-9]+:[0-9]+: error:'. The claim that Xcode 26 ships the Metal Toolchain as a separate downloadable component comes from Xcode 26 release knowledge, not from the research files. It must be confirmed with one CI run before any .metal file lands. Fix: Build 3: no .metal files. Use per-face LowLevelMesh parts, or ShaderGraphMaterial(materialXLabel:data:), which verify/rendering-viewer.json confirms is iOS 18.0 and recommends 'first (no Metal toolchain dependency in CI)'. Before build 4, land a one-kernel canary .metal file on its own branch, add `xcodebuild -downloadComponent MetalToolchain` (if needed) and a '\.metal:' error grep to the workflow, and ship the CPU texturing path first as the default.
- fidelity-first: The shared-type contract is not compilable as written, and one Core module blocks every agent. Evidence: Core types are given as tables, not Swift. CleanWall.baseLine uses `Segment3`, but the Geometry folder only has Segment2D. ElementEvidence.roomPlanConfidence uses an undefined `ConfidenceLevel`. TextureReport has a field called 'stage timings'. `protocol PipelineStage { associatedtype Input; associatedtype Output ... }` is used by a heterogeneous scheduler, which needs type erasure in Swift 5.9. Capture, Processing and Texture are each 'two agents' in one folder. Fix: Publish Core as a compiling Swift file before any other agent starts: one CI run, all types spelled out, missing types added to Geometry (Segment3) or Core (a DetectionConfidence enum). Make the scheduler run `[AnyPipelineStep]` closures with a product enum. Split each two-agent module into two folders with disjoint files.
- fidelity-first: 'Remove original photos' deletes raw keyframes. Evidence: Section 2.1: 'that is the one explicit, user-confirmed exception to "raw is never deleted"'. Task constraint: raw scan data is never modified. SPEC: 'Never destroy the original raw scan when the user edits the project.' Fix: Offer the storage saving only as archive or export plus deletion of the whole project, or move the keyframes into a user-exported backup before deleting them. Alternatively limit it to derived/ and superseded scans, as UX-first's 'Free up space' does.
- ux-first: Plane detection is on during room scans, so ARKit flattens the raw LiDAR mesh that the spec requires to be high-detail. Evidence: Section 3.2 step 2: `planeDetection = [.horizontal, .vertical]` for Room, House and Advanced. raw/arkit-mesh-depth.json: 'if plane detection is also enabled ARKit flattens the mesh where it detects a plane'. Ship-first and fidelity-first both set planeDetection = [] for rooms for exactly this reason. Fix: Set planeDetection = [] for Room, House and Advanced space. Enable [.horizontal, .vertical] only for Quick Measure, and for the large-object floor seed if needed (or use the floor-classified mesh instead).
- ux-first: Build 3 uses the headless RoomCaptureSession with its own ARView and coaching off, which is the path where sceneDepth is reported dropped, and it gives up Apple's live outlines. Evidence: verify/arkit-mesh-depth.json: the RoomCaptureView 'preserves' sentence 'may hold for the view path, it does not hold for the headless session'. Forum 763400: 'sceneDepth is no longer present on the incoming ARFrames'. Section 3.2 step 4 sets isCoachingEnabled = false and replaces the outlines with a custom RoomOutlineOverlay, which means extra code and device risk in the first capture build. Fix: Build 3 should host RoomCaptureView(frame:arSession:) with coaching on and only a minimap, as ship-first and fidelity-first do. Move the own-ARView overlay behind a feature flag in a later build, after the build 3 diagnostics log shows depth and mesh survive.
- ux-first: A @MainActor ScanEngine protocol whose implementations do their work on capture.queue will not compile in Swift 5.9 without restructuring. Evidence: Section 3.1: `@MainActor protocol ScanEngine`. Section 3.3: 'RoomScanEngine builds a LiveScanSnapshot on capture.queue at 4 Hz'. Declaring the conformance on the class infers main-actor isolation. verify/storage-deploy.json: 'actor-isolation checking still runs wherever code has adopted concurrency, and those violations are hard errors even in Swift 5 mode ... calling a @MainActor-isolated function or property from a synchronous nonisolated context'. Fix: Split each engine into a nonisolated NSObject recorder (the ARSessionDelegate and RoomCaptureSessionDelegate on capture.queue, holding value-type state) and a @MainActor facade that conforms to ScanEngine and receives Sendable snapshots through DispatchQueue.main.async.
- ux-first: Sealing raw folders with POSIX 0o555 and 0o444 permissions breaks Delete, Duplicate, Free up space and restore. Evidence: Section 2.1: 'sets POSIX permissions to read-only (0o444 files, 0o555 folders)'. POSIX filesystem behaviour, not taken from the research: unlinking an entry requires write permission on its directory, so FileManager.removeItem on a package containing 0o555 directories fails partway. Section 8.9 lists Delete and 'Free up space' of superseded scans as operations on these folders. Fix: Drop the chmod and enforce immutability in code (RawScanWriter is the only writer, and SEAL.json sizes and hashes are verified on open). Otherwise ProjectStore must restore u+w recursively before any delete or move.

### Summary

Winner: ship-first, 48 of 60. UX-first scores 44 and fidelity-first 37.

**Ship-first** is the only plan that fits the real limits: every compile is a CI round trip, the target is Swift 5.9 mode on iOS 18.0, and many agents work in parallel.
- **No risky compile paths.** It has no Metal, no macros, no SceneKit and no vertex-color shader. Coverage and classification colors use LowLevelMesh parts with UnlitMaterial, which verify/rendering-viewer.json confirms "need no shaders".
- **Low-risk first build.** Build 3 uses QuickLook for 3D and RoomCaptureView(frame:arSession:) for capture. That is the view path the verify files say is most likely to keep the session config, and it adds the re-apply in didStartWith plus a watchdog. Planes are off for rooms.
- **Parallel-friendly.** The shared types are real Swift declarations, the modules are small with one folder each, strings go in Copy+X extensions, and project.yml has a single owner. Estimate: 1 to 3 CI round trips per module.

Ship-first still needs these fixes:
- **House alignment.** StructureBuilder moves rooms and regenerates room IDs, which leaves the mesh and textures out of line with the merged model. Store a per-room transform, matched on the surface identifiers the merge keeps.
- **Backups.** Replace the in-memory ZipWriter with a streaming zip.
- **Keyframe encoding.** Move the JPEG encode off the ARKit delegate queue, using a pixel-buffer pool.
- **Edits.** Use one undoable edit log for both the plan and 3D, instead of two separate stores.
- **Large objects.** Add a large-object mesh path with side coverage, which gives the spec's "Capture the left side" guidance.

**UX-first** has the best amateur flow. Its fake scan engine is the best idea for parallel work and should be grafted. It has four problems that would stop it:
- Plane detection is on during room scans. Research says this flattens the raw LiDAR mesh (raw/arkit-mesh-depth.json).
- Build 3 runs RoomPlan headless with coaching off. That is the path where depth is reported lost.
- A @MainActor scan protocol whose engines work on the capture queue. The verify files say actor-isolation violations are hard errors even in Swift 5 mode.
- Sealing raw folders with read-only POSIX permissions (0o555), which would make project delete fail.

**Fidelity-first** covers the most of the spec: honest surface evidence, a mesh-refined clean model, ICP room alignment and calibrated confidence. It is the hardest to compile:
- Metal files arrive in builds 3 and 4, and the CI error grep only matches .swift files.
- The shared types are tables, not Swift, and some referenced types do not exist (Segment3, ConfidenceLevel).
- It deletes original photos, which breaks the raw-data rule.

Take its capture ideas (anchor-local raw mesh, per-frame intrinsics, pose track), its forbidden-names list, and its diagnostics self-tests into build 3. Add its refinement and evidence stages only in later builds.

The claim that Xcode 26 needs a separate Metal toolchain download does not come from the research files. Confirm it with one CI run before any .metal file lands.

No files were edited.

## Judge: Product owner (SPEC.txt coverage)

Winner: **ship-first**

| Proposal | Spec | Build | Perf | UX | Risk | Parallel | Total |

| ship-first | 7 | 9 | 7 | 7 | 8 | 9 | 47 |

**ship-first**: SPEC walk: Room (RoomPlan with a shared-session mesh, keyframes and depth recorded from build 3), House (one RoomCaptureView and ARSession per visit, world map after every room, manual AlignRoomsScreen, floors by elevation), Object (port of GuidedCapture, crop by re-running with PhotogrammetrySession.Request.Geometry, which exists per raw/object-capture.json), Realistic (cell texture in B5, chart atlas in B6), Raw (mchk plus classification colors), Clean (CleanModel from CapturedRoom with provenance flags), 2D plan (one Plan2D shared by Canvas, PDF, SVG and DXF), measurements with a research-based sigma and a RoomPlan cap, exports mapped to the existing writers, and a full project system. All of these are covered. The gaps: (1) Room mode never shows live GREEN/YELLOW/RED/GRAY on the forming mesh. It gets only a minimap, and the colored overlay exists only in LiveMeshScreen (space scans and patch passes, B5). (2) Large objects and vehicles have no isolated-object path. Advanced 'An object' goes only to Object Capture, which is capped at .reduced. (3) No mesh refinement: ceiling height is the median wall height, labeled inferred, and there is no hole filling or decimation. (4) The headline texture requirement arrives late: Textured in B5, Photo Realistic in B6. (5) PlanEditor operations like merge and split room are only listed as 'editing ops'. Best first shippable build: B3 already has a quality screen from voxel coverage, the floor plan, measurements, USDZ/JSON/PDF/SVG/DXF exports and QuickLook 3D and AR, with zero custom 3D renderer. Buildability is the strongest of the three: no Metal, no CustomMaterial, per-face color through LowLevelMesh parts plus UnlitMaterial (matching verify/rendering-viewer.json 'Per-FACE colors ... need no shaders'), and modules capped at 900 lines with per-module Copy extensions. Risks: backup through the in-memory ZipWriter, deleting raw keyframes and Checkpoint, and trusting floors[0].polygonCorners (see fatal flaws).

**fidelity-first**: Closest match to the SPEC text. Representation A is the most faithful: anchor-local mesh plus transform, a 10 Hz pose track, per-frame intrinsics and exposure, depth plus confidence, and a SessionQualityLog. Representation B covers exposure, seams and hole filling 'where mathematically reasonable' (a gain solve, then seam levelling, photo-consistency rejection and holeFilled provenance). Representation C refines RoomPlan with the mesh (IRLS wall planes, a ceiling measured from ceiling faces as the SPEC asks, refined jambs, and counter/cabinet/column heuristics labeled recognizer). HIDE FURNITURE is honest thanks to a per-cell measured/estimated/inferred/occluded/unscanned evidence map. Measurement confidence is the best of the three: path-length pose drift, local fit sigma, and a k_cal constant calibrated against TEST_PLAN. There is a large-object path for vehicles and appliances, and ICP alignment. Cost: build 3 already needs a LowLevelMesh viewer with a vertex-color preview. verify/rendering-viewer.json says the CustomMaterial and ShaderGraphMaterial paths are unconfirmed for LowLevelMesh .color on iOS ('verify both render LowLevelMesh .color on device in an early build'). Build 4 is overloaded: a Metal depth pass, view-selection and bake kernels, mesh refinement, the evidence map, a live overlay on a custom ARView that replaces RoomCaptureView, Quick Measure and Advanced, all compiled with no local compiler. Owner sizes of 1100 to 1500 lines need 'two agents' per module, so parallelism is lower. Exposure capping via configurableCaptureDeviceForPrimaryCamera carries Apple's warning from raw/texturing.json: 'Apple warns strong changes hurt ARKit's tracking/semantics'. Objects and House do not arrive until B5. Every Metal component has a named CPU fallback, which is good risk hygiene, but the amount of novel numerical code (ICP, TSDF, quadric decimation, IRLS) that can only be validated on device is the largest of the three. Backup uses the in-memory ZipWriter, and it also trusts floors[].polygonCorners.

**ux-first**: The best amateur flow of the three. Quality check, Show Missing Areas and the House room list are sheets over the still-live camera. Processing is progressive (the plan in seconds, then the mesh, then color). A degraded-mode table is designed into the UI, and there is a small-versus-large object chooser, the Large path with 8-sector plus top side guidance ('Capture the back/left', which the SPEC asks for and Object Capture cannot give), photo pins that fly the camera to the viewpoint, a full edit-op enum with undo covering every SPEC floor plan edit, and provenance on everything. The ScanEngine/LiveScanSnapshot contract, with FakeScanEngine and SnapshotRecorder replaying real device scans, gives the best parallel implementability: UI agents never need ARKit. StreamingZip correctly notes that the existing ZipWriter builds Data in memory. It also never thins raw ('Raw is never thinned afterwards'). Buildability suffers from several API misuses: isCoachingEnabled = false while still expecting didProvide instructions, planeDetection on during Room raw capture, ExpectedSurfaces taken from wall polygonCorners, and a custom ARView replacing RoomCaptureView in the very first scanning build (unresearched with a shared RoomPlan session, and it throws away Apple's polished live outlines). POSIX read-only raw (0o444 files, 0o555 folders) will break Delete, Duplicate and Restore unless every path chmods first. The keyframe gate of 0.5 m or 20 degrees at Standard is sparser than raw/texturing.json recommends ('camera moved > ~15 cm or rotated > ~10 degrees'), which hurts textures. Photo Realistic equals Textured until B7, and House mode is last (B6).

### Ideas to graft

- From ux-first: Adopt the @MainActor ScanEngine protocol plus the LiveScanSnapshot value contract, FakeScanEngine, SnapshotRecorder (JSON Lines of real device snapshots) and a demo mode in Settings. Why: With CI as the only compiler and cloud agents that cannot scan, UI modules (AppShell, QualityUI, HouseUI, Results) can be built and exercised on the phone before the capture modules work. This also removes ship-first's hidden coupling of UI to ARSessionHub and RoomCaptureController.
- From ux-first: Designed degraded-mode table (all works / depth stripped / mesh and depth stripped / RoomPlan failed), with layout-only coverage painted on RoomPlan boxes. Why: Ship-first has a watchdog and a two-pass fallback, but no UX spec for each failure row. The UX-first table turns the top research risk (verify/arkit-mesh-depth.json: 'sceneDepth (and possibly other frameSemantics / videoFormat) disappears') into defined user-visible behavior.
- From ux-first: Object size chooser: Small/medium goes to Object Capture; Large goes to the LiDAR mesh path with a tap-seeded gravity OrientedBox, SectorCoverage side guidance and a crop edit. Why: The SPEC lists vehicles, appliances, machines and equipment, and asks for 'Capture the left side / back'. Object Capture is capped at .reduced (<50k triangles, 2048 textures) and exposes no pose. Ship-first has no large-object path.
- From ux-first: StreamingZip (FileHandle based, STORE) for Back Up and Restore, with restore into a staging folder, validation, then a move. Why: The existing ios/Sources/Export/ZipWriter.swift builds the whole archive in memory (`func finish() throws -> Data`). Ship-first quotes 200 to 350 MB per room, so a house backup would be killed by jetsam.
- From ux-first: Quality sheet as a medium-detent sheet over the live camera, the TourHUD with a suggested standable viewpoint 1.5 m off the missing area, and window/mirror exclusion from missing areas. Why: Makes 'SHOW MISSING AREAS should guide the user directly' concrete and avoids nagging about surfaces LiDAR cannot see.
- From ux-first: Progressive processing with per-tab chips ('Adding color and texture 40%') and an explicit 'Viewer opens after' per mode. Why: Ship-first already opens results after floorPlan; UX-first specifies it for every mode, including object and space scans.
- From fidelity-first: Store raw mesh chunks anchor-local plus their transform (as ARKit delivered them), and add a 10 Hz binary pose track with tracking, thermal and exposure per sample. Why: The SPEC's Representation A asks for world transforms, timestamps and orientation. Anchor-local storage loses no precision and allows re-posing after alignment. The pose track feeds the path-length drift term in confidence.
- From fidelity-first: Surface evidence map (5 cm cells: measured, estimated, occluded by BVH ray test toward keyframe positions, unscanned, inferred), used by HIDE FURNITURE and by measurement grading. Why: Ship-first's occludedSpans heuristic (movable object within 0.3 m of a wall) does not show what was actually seen. The SPEC requires that occluded regions be marked, not fabricated.
- From fidelity-first: Mesh-refined clean model as an optional stage with strict acceptance tests (wall plane IRLS fit, ceiling height from ceiling-classified faces, jamb refinement), keeping both the RoomPlan value and the refined value. Why: RoomPlan has no ceiling. Ship-first's median wall height labeled 'inferred' leaves the SPEC's ceiling height and door width items weak. The acceptance tests keep this safe.
- From fidelity-first: Confidence model with sigma_pose = L*r + 0.01*s (camera path length between the best observations), k_cal set from TEST_PLAN section 3, and every term logged. Why: It is better grounded than a pose term that scales only with length, and it can be recalibrated from logs without rescanning.
- From fidelity-first: Build 3 Diagnostics: projection dots on the live image, depth reprojection round trip under 0.5 px, and a numbered UV checkerboard in RealityKit. Why: This settles the texture conventions two builds before any texturing code relies on them. Ship-first plans the UV test pattern for B4 only.
- From fidelity-first: Per-room rigid alignment transforms (structure/alignment.json), applied to mesh and keyframes after StructureBuilder, with the conservative 4-DOF doorway ICP as a later refinement. Why: verify/floorplan-cad.json says merged output can be 'moved' and 'room and floor identifiers are regenerated', so session-frame meshes and keyframes will not line up with the merged clean model unless the transform is computed and stored.

### Fatal flaws

- all three: Room outline and floor area come from floors[0].polygonCorners, with the wall loop only as a fallback. On L-shaped or multi-section rooms the floor area, perimeter, room length and width, and the plan outline will be wrong. Evidence: verify/floorplan-cad.json (refuted claim): 'in a real encoded CapturedRoom ... the single floor polygon is a 4-corner rectangle (6.43 x 7.43 m, 47.7 m2) equal to the bounding box of an L-shaped, multi-section scan ... Compute area/perimeter from the closed wall loop (endpoints from wall transforms), use the floor polygon only as a fallback or cross-check, and flag a mismatch.' Ship-first 4.3: 'Floor: floors[0].polygonCorners ... fallback to the closed wall polygon'. Fidelity 4.4A and UX-first 4.2 CleanModelBuilder do the same. Fix: Make the closed wall loop (wall endpoints from transform times (+/- dimensions.x/2, 0, 0, 1), intersected at corners) the primary outline. Use polygonCorners only as a cross-check and log mismatches. Add an L-shaped room fixture to the RoomModel self-test.
- all three (ship-first most exposed): House merge assumes StructureBuilder keeps the input frames and identifiers, and that a failed merge throws. Edits keyed by RoomPlan identifiers and session-frame meshes and keyframes will then silently misalign or orphan, and rooms from unrelocalized sessions will stack without an error. Evidence: verify/floorplan-cad.json: 'rooms from separate unrelocalized sessions ... merge without an error and come out stacked on top of each other ... do not assume rooms keep their exact input transforms after merging: developers report the merged output being moved, and room and floor identifiers are regenerated.' Ship-first 2.2: Overrides 'keyed by RoomPlan identifiers or our ids; survives re-derivation', and 3.3 relies on a merge failure to open AlignRoomsScreen. Fix: Only pass rooms whose frame is confirmed shared (same session, or relocalized with tracking normal) to StructureBuilder. After the merge, match walls pre and post merge to recover each room's rigid transform, and apply it to the mesh, keyframes and plan. Key all edits by Mapper's own stable ids, with a sourceID mapping table rebuilt after every merge. Add an overlap check that sends stacked rooms to manual alignment.
- ux-first: RoomPlan coaching is disabled (`isCoachingEnabled = false`) while the design still consumes `didProvide instruction`. RoomPlan will then send no instructions, so the moveSlower, tooClose, moveCloser and lightingPoor detectors that depend on slowDown, moveAwayFromWall, moveCloseToWall and turnOnLight never fire. Evidence: verify/ui-ux-patterns.json: 'Fetched configuration/iscoachingenabled.json: var isCoachingEnabled: Bool, introducedAt 16.0, discussion says the framework calls captureSession(_:didProvide:) with an Instruction when enabled, default value true.' UX-first 3.2 step 4: 'isCoachingEnabled = false (our guidance replaces RoomPlan's coaching text; we still consume didProvide instruction)'. Fix: Keep isCoachingEnabled = true, and suppress RoomPlan's own text simply by not using RoomCaptureView (headless RoomCaptureSession draws nothing). Alternatively keep RoomCaptureView, as ship-first does, and suppress Mapper's tier 2 and 3 messages while Instruction != .normal.
- ux-first: Room and House capture run with planeDetection = [.horizontal, .vertical], which flattens the recorded raw LiDAR mesh where planes are detected. The 'raw' scan is therefore altered at capture time, against SPEC 'preserve the highest practical amount of sensor data'. ExpectedSurfaces for coverage is also built from wall polygonCorners, which are empty for ordinary walls. Evidence: raw/arkit-mesh-depth.json: 'Plane-flattening and people-occlusion mesh-removal notes match the doc discussion verbatim' (fidelity cites this as arkit F0: 'ARKit flattens the mesh where it detects planes'). verify/floorplan-cad.json: 'rectangular walls have polygonCorners == [] (all 20 walls in the sample), so wall code must fall back to transform + dimensions.' UX-first 3.2 step 2 and 3.3: 'ExpectedSurfaces (walls with polygonCorners, openings subtracted, floors)'. Fix: Set planeDetection = [] for Room, House and Advanced space, and turn it on only for Quick Measure, as ship-first and fidelity do. Build expected wall rectangles from transform and dimensions, and use polygonCorners only when non-empty.
- ship-first: Raw data is destroyed: 'Keep all photos: Off: keyframes deleted after texturing succeeds', and the Object Capture Checkpoint under raw/objects is deleted. Backup/restore runs through the in-memory ZipWriter for packages of hundreds of MB to several GB. Evidence: SPEC: 'Never destroy the original raw scan when the user edits the project.' ios/Sources/Export/ZipWriter.swift exposes `func finish() throws -> Data` and `static func archive(_ entries: [(name: String, data: Data)] ...) -> Data`. Ship-first gives '200 to 350 MB per room' and states M38 'backup (ZIP via M03)'. Fix: Thin keyframes at capture time (a coarser gate), never afterwards. Keep Checkpoint in derived/ or a cache folder rather than raw/. Offer only an explicit, confirmed 'Remove original photos' action, as fidelity does. Replace the backup path with a FileHandle-streaming STORE zip, as UX-first does.
- fidelity-first: Metal shaders (Texture.metal, Render.metal) and a CustomMaterial vertex-color preview sit on the critical path of builds 3 and 4, with no local compiler and no on-device confirmation that either material path renders LowLevelMesh .color on iOS. Build 4 alone stacks GPU texturing, mesh refinement, the evidence map, a custom live ARView replacing RoomCaptureView, Quick Measure and Advanced. Evidence: verify/rendering-viewer.json: 'for true per-vertex color, try ShaderGraphMaterial(materialXLabel:data:) first (no Metal toolchain dependency in CI) and keep CustomMaterial as fallback; verify both render LowLevelMesh .color on device in an early build.' raw/rendering-viewer.json: 'neither path has been seen rendering a LowLevelMesh .color attribute in an iOS-compiled sample'. Fidelity risk 9 itself says the ARView on a shared RoomPlan session is 'not researched directly'. Fix: Ship the build 3 preview as per-face colored LowLevelMesh parts (no shader). Start the texturer on the CPU path (ScanSpace-style CoreGraphics bake) and add Metal kernels only behind a device benchmark gate after the CPU atlas is correct. Split build 4 so texturing and refinement land separately from the live-overlay change.
- ux-first: Sealed raw folders are made read-only on disk (0o444 files, 0o555 folders). FileManager removeItem, Duplicate (copyItem keeps modes) and Restore-over-existing will fail or leave undeletable trees unless every path restores permissions first, so the Delete action required by the SPEC project system can break. Evidence: UX-first 2.1: 'RawScanWriter.seal() ... sets POSIX permissions to read-only (0o444 files, 0o555 folders)'. This is not in the research (a grep of docs/research for posix/0o444 finds nothing), so it is an unverified mechanism. Fix: Enforce immutability in the API (only RawScanWriter writes, plus SEAL.json size and hash verification on open) rather than with file modes. Or centralize a chmod-back step in ProjectStore.delete, duplicate and restore, with a self-test.

### Summary

I walked SPEC.txt section by section, and all three proposals cover the full scope: room, house room by room, object, the realistic textured model, raw mesh, clean model, 2D plan, measurements with confidence, exports, projects, and guidance for amateurs.

**Winner: ship-first, 47, just ahead of ux-first at 46; fidelity-first 40.** It has the most buildable and most parallel plan, and it ships the most useful build 3: a real quality screen, floor plan, measurements, PDF/SVG/DXF/USDZ exports and QuickLook 3D and AR, with no Metal and no custom renderer. Its gaps:
- Textures arrive late: Textured in build 5, Photo Realistic in build 6.
- In Room mode the live green/yellow/red/gray coloring only appears on a minimap.
- There is no large-object or vehicle path.
- It does not refine the clean model from the mesh; ceiling height is inferred from wall heights.

**Fidelity-first** matches the SPEC most closely: anchor-local raw mesh plus a pose track, mesh-refined walls and ceiling, an evidence map that makes Hide Furniture honest, seam and exposure handling, and calibrated confidence. It has the weakest buildability and parallelism. Metal and CustomMaterial are on the critical path in builds 3 and 4, and verify/rendering-viewer.json says to try ShaderGraphMaterial first because it needs no Metal toolchain in CI. Its modules need two agents each, and build 4 is overloaded.

**UX-first** has the best amateur experience: quality and house sheets over the live camera, progressive results, designed degraded modes, and a small-versus-large object chooser. It also has the best parallel contract: a ScanEngine interface plus FakeScanEngine and SnapshotRecorder, so UI agents never touch ARKit. But it misuses APIs:
- It sets isCoachingEnabled = false, which stops RoomPlan's didProvide instructions (verify/ui-ux-patterns.json).
- It turns planeDetection on during raw room capture, which flattens the raw mesh (raw/arkit-mesh-depth.json).
- It builds expected wall surfaces from wall polygonCorners, which are empty for ordinary rectangular walls (verify/floorplan-cad.json).
- It makes sealed raw folders read-only on disk, which will break Delete and Duplicate.

**Flaws shared by all three:**
- Room outline and floor area come from floors[0].polygonCorners. In practice that is a bounding rectangle for L-shaped rooms (verify/floorplan-cad.json), so the closed wall loop must be the primary source.
- House merge assumes StructureBuilder keeps room positions and identifiers. The research says merged output can move, identifiers are regenerated, and rooms from unaligned sessions stack without any error.
- Ship-first and fidelity-first back up projects through the existing ZipWriter, which builds the whole archive in memory. That will crash on multi-GB house projects.

**What to build:** use ship-first as the base, with these changes:
- From UX-first: the ScanEngine contract, fake engine and demo mode; the degraded-mode UX; the large-object path; a streaming zip for backup; and the quality sheet over the live camera.
- From fidelity-first: anchor-local raw mesh plus a pose track; the evidence map; mesh-refined ceiling and walls with acceptance tests; the path-drift confidence term with a calibration constant; the projection and UV diagnostics in build 3; and per-room alignment transforms.
- Wall-loop outlines and edits keyed by Mapper's own stable ids.
- No deleting raw keyframes or the Object Capture checkpoint; thin photos only at capture time.

The other two:
- ux-first has the best data model and amateur UX, but its capture layer turns on plane detection for rooms (verify: "ARKit flattens the mesh on detected planes"). It also runs the heaviest live stack: headless RoomPlan plus its own ARView, overlays and a minimap, with RoomPlan kept running through the quality sheet and tour. It reads wall polygonCorners, which are empty for rectangular walls. Its chmod sealing breaks deletion.
- fidelity-first has the best recorder and the most spec coverage, but it pins a non-default videoFormat and an exposure cap under RoomPlan (verify: "do not depend on a non-default videoFormat during RoomPlan"). Metal lands in builds 3 and 4, and builds 3 and 4 are too large for parallel agents without a compiler.

Flaws shared by all three:
- They derive room area from floors[0].polygonCorners, which verify/floorplan-cad #8 refutes: in a real sample it was the bounding rectangle of an L-shaped scan.
- None budgets memory for a whole-house continuous session.
- They all follow Apple's Object Capture flow, which rebuilds ObjectCaptureView between passes and can leak 250 to 500 MB each time, then run photogrammetry in the same process.

Nothing in the repo was edited.
